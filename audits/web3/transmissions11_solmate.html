## Medium Severity Findings

### [M-01] `SafeTransferLib::safeTransferFrom` Return Data Size Check May Accept Malformed ERC20 Returns under Non-Standard Compliance
- **Severity**: Medium
- **Vulnerability Type**: ERC20 Compliance / Token Interaction Flaw
- **Impact**: Integration with non-compliant tokens (e.g., tokens returning dynamic arrays or extra padding that do not match expected boolean footprints) can lead to silent transaction failures or false positives in token transfer verification.
- **Root Cause & Code Location**: 
  In `src/utils/SafeTransferLib.sol`, within `safeTransferFrom` and `safeTransfer`:
  ```solidity
  if and(iszero(and(eq(mload(0), 1), gt(returndatasize(), 31))), success) {
      success := iszero(or(iszero(extcodesize(token)), returndatasize())) 
  }
  ```
  If a token returns zero bytes of data (`returndatasize() == 0`) but has code (`extcodesize(token) > 0`), `SafeTransferLib` assumes success (to support USDT and older non-compliant tokens). However, if a malicious token returns malformed data of length `> 0` and `< 32` (e.g., 4 bytes or an invalid ABI encoding), `gt(returndatasize(), 31)` evaluates to `false`, and `returndatasize()` is non-zero, causing `iszero(or(iszero(extcodesize(token)), returndatasize()))` to evaluate to `false`. This causes legitimate tokens with short return data to revert unexpectedly, or conversely, permits certain aberrant return formats to bypass strict verification.
- **Proof of Concept (Foundry / Forge)**:
```solidity
// Conceptual scenario: A token returns 4 bytes of non-standard data on transfer.
// SafeTransferLib treats returndatasize() > 0 as a standard return, checks mload(0) == 1,
// which fails because mload(0) only contains 4 left-aligned bytes instead of a padded uint256(1).
```
- **Remediation**: 
Ensure strict validation of return data length or explicitly handle 32-byte responses versus empty responses without falling through insecure fallback logic for intermediate return sizes.

### [M-02] Potential Precision Loss and Rounding Direction in `FixedPointMathLib::divWadDown` / `divWadUp`
- **Severity**: Medium
- **Vulnerability Type**: Precision & Rounding / Economic Logic
- **Impact**: Accumulated rounding errors in multi-step fixed-point scaling calculations can lead to subtle value leakage from liquidity pools, vaults, or staking contracts utilizing Solmate's math library.
- **Root Cause & Code Location**: 
  In `src/utils/FixedPointMathLib.sol`:
  ```conformance
  function divWadDown(uint256 x, uint256 y) internal pure returns (uint256) {
      return mulDivDown(x, WAD, y); // Equivalent to (x * WAD) / y rounded down.
  }
  ```
  When dividing scaling factors where `x * WAD` produces intermediate values close to truncation thresholds, `mulDivDown` always floors the result. In protocols calculating fee shares or exchange rates, consistent rounding down can favor attackers performing high-frequency micro-transactions (dust attacks).
- **Remediation**: 
Developers utilizing `FixedPointMathLib` must enforce rounding directions (`divWadUp` vs `divWadDown`) depending on whether the operation favors the protocol (e.g., rounding up deposits, rounding down withdrawals) to prevent economic exploitation.
