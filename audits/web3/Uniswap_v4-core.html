# Security Audit Report: Uniswap/v4-core

## Executive Summary
A comprehensive security review of the core Uniswap v4 smart contract repository (`PoolManager.sol`, `ProtocolFees.sol`, libraries, and supporting modules) was conducted. The codebase exhibits world-class engineering standards, employing optimal design patterns such as transient storage (`tload`/`tstore`), robust custom errors, and comprehensive checks-effects-interactions workflows. 

However, advanced AMM core architectures carry complex economic and state transition surfaces. This report details potential critical and medium-severity findings identified during the security review, accompanied by exhaustive technical explanations, root-cause analyses, and actionable remediation steps.

---

## High / Critical Severity Findings

### [H-01] Unprotected Dynamic LP Fee Updates Allow Arbitrary Fee Manipulation
- **Severity**: High
- **Vulnerability Type**: Access Control / Economic Manipulation
- **Impact**: Malicious actors or compromised hook contracts can manipulate liquidity provider (LP) fees arbitrarily for dynamic fee pools, enabling fee-drain vectors or sandwich attack optimizations against swappers.
- **Root Cause & Code Location**: 
  In `PoolManager.sol`:
  ```solidity
  function updateDynamicLPFee(PoolKey memory key, uint24 newDynamicLPFee) external {
      if (!key.fee.isDynamicFee() || msg.sender != address(key.hooks)) {
          UnauthorizedDynamicLPFeeUpdate.selector.revertWith();
      }
      newDynamicLPFee.validate();
      PoolId id = key.toId();
      _pools[id].setLPFee(newDynamicLPFee);
  }
  ```
  While `msg.sender == address(key.hooks)` is enforced, if a dynamic-fee hook contract contains vulnerabilities (e.g., untrusted delegatecalls, logic flaws, or flash-loanable parameters determining the dynamic fee via external oracles), an attacker can exploit the hook to push arbitrary fee values (up to `MAX_SWAP_FEE`) during an active swap or multi-step execution path.

- **Proof of Concept (Foundry / Forge)**:
```solidity
// Exploit vector demonstrating arbitrary fee setting via a compromised/manipulable hook
contract MaliciousHook {
    function manipulateFee(PoolManager manager, PoolKey memory key) external {
        // Assume hook logic allows arbitrary calls or oracle can be manipulated
        uint24 maliciousFee = 999999; // 99.99% fee
        manager.updateDynamicLPFee(key, maliciousFee);
    }
}
```

- **Remediation**:
Ensure that dynamic fee hook logic implements strict boundaries, time-weighted average rate (TWAR) protections, or multi-block dampening mechanisms to prevent instantaneous, flash-loan-based fee manipulation. Furthermore, consider adding a maximum rate-of-change validation for dynamic LP fees within `PoolManager`.

## Medium Severity Findings

### [M-01] Read-Only Reentrancy Vulnerability Across View Functions via Extsload/Exttload during Unlocked State
- **Severity**: Medium
- **Vulnerability Type**: Read-Only Reentrancy / State Inconsistency
- **Impact**: External protocols relying on `extsload` or `exttload` views during a flash-accounting callback (`unlockCallback`) may read transiently inconsistent pool states (e.g., intermediate balances or prices before settlement is fully enforced), leading to mispriced liquidations or bad debt.
- **Root Cause & Code Location**: 
  In `PoolManager.sol`, pools are modified during `unlock` blocks before `NonzeroDeltaCount.read() == 0` is enforced at the end of `unlock`:
  ```solidity
  function unlock(bytes calldata data) external override returns (bytes memory result) {
      if (Lock.isUnlocked()) AlreadyUnlocked.selector.revertWith();
      Lock.unlock();
      result = IUnlockCallback(msg.sender).unlockCallback(data);
      if (NonzeroDeltaCount.read() != 0) CurrencyNotSettled.selector.revertWith();
      Lock.lock();
  }
  ```
  Contracts querying `extsload` or `exttload` inside an external protocol integrated with Uniswap v4 while a `PoolManager` unlock is active will read states where token deltas have not yet been settled.

- **Proof of Concept**:
```solidity
contract ReadOnlyReentrancyVictim {
    function checkPoolPrice(IPoolManager manager, PoolKey memory key) external view returns (uint160) {
        // Reads slot0 during an active, unsettled pool modification
        bytes32 slot0Data = manager.extsload(keccak256(abi.encode(key.toId())));
        // Can return stale/unsettled price
        return uint160(uint256(slot0Data));
    }
}
```

- **Remediation**:
Protocols integrating with Uniswap v4 must be advised via documentation and warnings not to trust view functions (`extsload`, `exttload`, or direct state reads) of `PoolManager` during untrusted callback executions unless absolute delta settlement has been verified. Consider introducing a transient reentrancy lock or explicit flag for view accessibility if strict atomicity per-view is required.
