# Security Audit Report: compound-finance/compound-protocol

## Executive Summary
A comprehensive security review was performed on the selected core components of the Compound Protocol (`CErc20Delegator`, `CErc20Delegate`, `CErc20`, `CEther`, `SimplePriceOracle`, and `DAIInterestRateModelV3`). The codebase exhibits exceptional architectural patterns, specifically regarding upgradeability isolation (`CErc20Delegator` / `CErc20Delegate`) and handling of non-standard ERC-20 tokens. However, certain economic design choices, initialization patterns, and peripheral oracle implementations present critical and high-severity risks under specific market conditions or initial deployment vectors.

---

## High / Critical Severity Findings

### [H-01] Unprotected Initialization of Implementation Contract (`CErc20Delegate`)
- **Severity**: Critical
- **Vulnerability Type**: Access Control / Initialization
- **Impact**: An attacker can call `initialize(...)` on the uninitialized `CErc20Delegate` implementation contract directly, take ownership (`admin`), and potentially manipulate its storage or trigger malicious state transitions if the implementation contract is used incorrectly or interacts directly with proxies.
- **Root Cause & Code Location**: 
  The `CErc20Delegate` contract inherits from `CErc20` which exposes the `initialize(...)` function publicly without checking if it has already been initialized (e.g., missing an `initializer` modifier or check against `accrualBlockNumber != 0`). While `CErc20Delegator` delegates calls to `initialize` during deployment, the base implementation contract deployed on-chain is left uninitialized.
  - File: `contracts/CErc20.sol`, Function `initialize(...)`
  - File: `contracts/CErc20Delegate.sol`

- **Proof of Concept (Foundry / Forge)**:
```solidity
contract DelegateInitializationExploit is Test {
    CErc20Delegate implementation;

    function setUp() public {
        implementation = new CErc20Delegate();
    }

    function testTakeOverImplementation() public {
        // The implementation contract is deployed uninitialized.
        // An attacker can call initialize directly on the implementation address:
        implementation.initialize(
            address(0), 
            ComptrollerInterface(address(0)), 
            InterestRateModel(address(0)), 
            1e18, 
            "Hacked", 
            "HACK", 
            18
        );
        
        // Attacker becomes or sets parameters inside the implementation context
    }
}
```

- **Remediation**:
In the `CErc20` `initialize` function, add a check to ensure it can only be initialized once (or deploy implementations with a constructor that automatically locks initialization).
```solidity
function initialize(...) public {
    require(accrualBlockNumber == 0, "market already initialized");
    super.initialize(...);
    // ...
}
```

### [H-02] First-Depositor / Share Inflation Vulnerability in `CErc20` (Donation Attack)
- **Severity**: High
- **Vulnerability Type**: ERC4626-style Vault Exploit / Exchange Rate Manipulation
- **Impact**: An attacker can manipulate the exchange rate (`exchangeRateStored()`) during the initial mint of a newly deployed cToken market, forcing subsequent depositors to lose funds due to integer rounding truncation when dividing by `totalSupply`.
- **Root Cause & Code Location**:
  The exchange rate is calculated based on:
  $$\text{ExchangeRate} = \frac{\text{getCash()} + \text{totalBorrows} - \text{totalReserves}}{\text{totalSupply}}$$
  When `totalSupply` is very small (e.g., 1 wei) after the first `mint()`, an attacker can directly transfer underlying tokens via `transfer` (without minting cTokens) to inflate `getCash()`. This drastically inflates the exchange rate. Subsequent minters will receive 0 cTokens due to rounding down in integer division unless their deposit size exceeds the inflated exchange rate threshold.
  - File: `contracts/CToken.sol` (inherited exchange rate calculations)
  - File: `contracts/CErc20.sol`

- **Proof of Concept (Foundry / Forge)**:
```solidity
function testShareInflationAttack() public {
    // 1. Attacker mints 1 wei of cToken
    cToken.mint(1);

    // 2. Attacker directly donates underlying tokens to the cToken contract
    underlying.transfer(address(cToken), 1e18);

    // 3. Victim tries to mint with 0.5e18 tokens -> receives 0 cTokens due to rounding down
    uint256 mintTokensBefore = cToken.balanceOf(address(victim));
    cToken.mint(0.5e18);
    uint256 mintTokensAfter = cToken.balanceOf(address(victim));
    
    assertEq(mintTokensAfter - mintTokensBefore, 0);
}
```

- **Remediation**:
Implement virtual shares / virtual assets offset (similar to ERC-4626 OpenZeppelin standard implementation) or enforce a minimum initial deposit (locking the first `1000` min-units to the zero address / dead address during `initialize`).

## Medium Severity Findings

### [M-01] `SimplePriceOracle` Lacks Access Control on `setUnderlyingPrice` and `setDirectPrice`
- **Severity**: Medium
- **Vulnerability Type**: Access Control / Economic Manipulation
- **Impact**: Any external user can call `setUnderlyingPrice()` or `setDirectPrice()` on `SimplePriceOracle` if it is used in production (or non-timelocked environments), allowing arbitrary manipulation of asset prices, leading to immediate uncollateralized borrowing and protocol insolvency.
- **Root Cause & Code Location**:
  - File: `contracts/SimplePriceOracle.sol`, Functions `setUnderlyingPrice` and `setDirectPrice` lack `onlyAdmin` or owner access control modifiers.
```solidity
function setUnderlyingPrice(CToken cToken, uint underlyingPriceMantissa) public {
    address asset = _getUnderlyingAddress(cToken);
    emit PricePosted(asset, prices[asset], underlyingPriceMantissa, underlyingPriceMantissa);
    prices[asset] = underlyingPriceMantissa;
}
```

- **Remediation**:
Restrict price updating functions to an authorized oracle updater or admin address:
```solidity
address public admin;
modifier onlyAdmin() {
    require(msg.sender == admin, "only admin");
    _;
}
function setUnderlyingPrice(CToken cToken, uint underlyingPriceMantissa) public onlyAdmin {
    // ...
}
```

### [M-02] Potential Division Precision Loss in `DAIInterestRateModelV3.dsrPerBlock()`
- **Severity**: Medium
- **Vulnerability Type**: Precision & Rounding
- **Impact**: Integer division ordering (`(pot.dsr() - RAY_BASE) / RAY_TO_BASE_SCALE`) truncates precision before multiplication by `SECONDS_PER_BLOCK`, potentially causing minor inaccuracies or zero-rates if base numbers are small.
- **Root Cause & Code Location**:
  - File: `contracts/DAIInterestRateModelV3.sol`, Line 84
```solidity
function dsrPerBlock() public view returns (uint) {
    return (pot.dsr() - RAY_BASE) // scaled RAY_BASE aka RAY
        / RAY_TO_BASE_SCALE // descale to BASE
        * SECONDS_PER_BLOCK; // seconds per block
}
```
Performing division before multiplication (`/ RAY_TO_BASE_SCALE * SECONDS_PER_BLOCK`) discards up to 9 decimals of precision prior to scaling back up.

- **Remediation**:
Multiply by `SECONDS_PER_BLOCK` first before dividing by the scaling factor to preserve decimal precision:
```solidity
function dsrPerBlock() public view returns (uint) {
    return ((pot.dsr() - RAY_BASE) * SECONDS_PER_BLOCK) / RAY_TO_BASE_SCALE;
}
```
