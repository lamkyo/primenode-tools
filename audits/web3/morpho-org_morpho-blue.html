# Security Audit Report: morpho-org/morpho-blue

## Executive Summary

**Contracts analyzed:** `src/Morpho.sol`, `src/libraries/*` (MathLib, SharesMathLib, UtilsLib, MarketParamsLib, SafeTransferLib, ConstantsLib), mocks (`OracleMock`, `IrmMock`, `ERC20Mock`, `FlashBorrowerMock`), and Certora harnesses (`MorphoHarness`, `MorphoInternalAccess`, `TransferHarness`, dispatch ERC20 variants).

**Overall posture:** The core protocol logic is defensively written — state is mutated before external calls in all fund-moving paths, share conversions consistently round in the protocol's favor, virtual shares/assets mitigate first-depositor inflation, and bad-debt socialization is handled at liquidation. The material risks concentrate in three areas:

1. **Oracle trust** — `liquidate` and `_isHealthy` consume a single `IOracle.price()` with no staleness, deviation, or bounds checks. A manipulated oracle is a direct path to wrongful liquidation and protocol bad debt.
2. **Centralization / access control** — a single `owner` can enable arbitrary IRMs (stateful, called during `_accrueInterest` on every market action) and set fees up to `MAX_FEE`, with no timelock or two-step transfer.
3. **Callback reentrancy surface** — callbacks fire *after* state updates but *before* token transfers in `supply`/`repay`/`liquidate`, and `flashLoan` permits unbounded reentry into any Morpho function within the same block.

**Risk level: Medium-High** — no unauthenticated theft path found in core accounting, but oracle integrity and owner privilege are single points of failure capable of draining or bricking markets.

## High / Critical Severity Findings

### [H-01] Manipulable Oracle Enables Wrongful Liquidation and Protocol Bad Debt

- **Severity**: High
- **Vulnerability Type**: Oracle Manipulation / Economic Attack
- **Impact**: An attacker who can influence `IOracle.price()` (spot-price oracles, thin liquidity, or a compromised/misconfigured oracle) can (a) force liquidation of perfectly healthy positions, seizing collateral at a discount via `liquidationIncentiveFactor`, and/or (b) allow undercollateralized borrowers to keep borrowing until the true price corrects, leaving `totalSupplyAssets` short and socializing bad debt to all suppliers.
- **Root Cause & Code Location**: `src/Morpho.sol` — `liquidate()` reads `IOracle(marketParams.oracle).price()` directly; `_isHealthy(...)` does the same. There is no staleness check, no min/max bound, no deviation check, and no TWAP. The oracle is trusted implicitly at whatever value it returns at `block.timestamp`.
```solidity
uint256 collateralPrice = IOracle(marketParams.oracle).price();
require(!_isHealthy(marketParams, id, borrower, collateralPrice), ErrorsLib.HEALTHY_POSITION);
// ... seizedAssets computed directly from collateralPrice
```
- **Proof of Concept (Foundry / Forge)**:
```solidity
// SPDX-License-Identifier: GPL-2.0-or-later
pragma solidity 0.8.19;
import "forge-std/Test.sol";
import "../src/Morpho.sol";
import "../src/mocks/OracleMock.sol";

contract OracleManipulationTest is Test {
    Morpho morpho;
    OracleMock oracle;
    address alice = address(0xA11CE);
    address attacker = address(0xBAD);

    function test_WrongfulLiquidation() public {
        // Setup: alice supplies collateral, borrows near max LLTV at price = 1e18.
        // Attacker (or oracle weakness) drops price to 1 wei for one block.
        oracle.setPrice(1); // collateral now worth ~nothing
        // Attacker calls liquidate with tiny repaidAssets, receives nearly all collateral
        // at the discounted liquidationIncentiveFactor.
        vm.startPrank(attacker);
        morpho.liquidate(marketParams, alice, type(uint128).max /*seized*/, 0, "");
        // alice's position is now liquidated despite being healthy at true price.
        vm.stopPrank();
        // When price reverts to 1e18, alice has lost collateral for no economic reason.
    }
}
```
- **Remediation**: Require oracle freshness and sanity bounds at the call site:
```solidity
function _price(IOracle oracle) internal view returns (uint256) {
    uint256 p = oracle.price();
    require(p > 0, ErrorsLib.ZERO_PRICE);
    // If the oracle exposes lastUpdate(), enforce:
    // require(block.timestamp - IOracleWithTimestamp(oracle).lastUpdate() <= MAX_STALENESS, "stale");
    return p;
}
```
Prefer oracles with built-in staleness/TWAP (e.g., Chainlink `latestRoundData` with `answeredInRound`/`updatedAt` checks) and enforce per-market price bounds.

### [H-02] Owner Can Enable Malicious IRM — Stateful External Call on Every Market Action

- **Severity**: High
- **Vulnerability Type**: Access Control / Privilege Escalation
- **Impact**: `enableIrm` is `onlyOwner` with no timelock, no multisig requirement, and no constraint on the IRM contract. The IRM's `borrowRate()` is invoked inside `_accrueInterest()`, which runs on `supply`, `withdraw`, `borrow`, `repay`, `withdrawCollateral`, `liquidate`, and `accrueInterest`. A malicious or buggy IRM can: revert to **brick all market operations**; return an arbitrarily large rate to **inflate `totalBorrowAssets`/`totalSupplyAssets`**, corrupting share pricing and enabling extraction of supplier funds; or reenter Morpho mid-accrual (state is partially updated: `totalBorrowAssets`/`totalSupplyAssets` increased, `lastUpdate` not yet written).
- **Root Cause & Code Location**: `src/Morpho.sol` — `enableIrm(address irm)` (only `onlyOwner`, no validation) and `_accrueInterest()`:
```solidity
uint256 borrowRate = IIrm(marketParams.irm).borrowRate(marketParams, market[id]);
uint256 interest = market[id].totalBorrowAssets.wMulDown(borrowRate.wTaylorCompounded(elapsed));
market[id].totalBorrowAssets += interest.toUint128();
market[id].totalSupplyAssets += interest.toUint128();
// ... feeShares minted ...
market[id].lastUpdate = uint128(block.timestamp); // written AFTER external call
```
- **Proof of Concept (Foundry / Forge)**:
```solidity
contract EvilIrm {
    // Returns 1e18 (100% per second) — compounds to astronomical interest in one accrual.
    function borrowRate(MarketParams memory, Market memory) external pure returns (uint256) {
        return 1e18;
    }
}
// Owner: morpho.enableIrm(address(evilIrm));
// Create market with irm = evilIrm, supply, wait 1 block, call any action:
// totalBorrowAssets and totalSupplyAssets both explode; share price desyncs from reality;
// borrowers can repay with worthless inflated shares or suppliers are diluted to near-zero.
```
- **Remediation**: This is partly by-design (owner trust), but harden it:
  1. Gate `enableIrm` behind a timelock + multisig (e.g., OpenZeppelin `TimelockController`).
  2. Move `market[id].lastUpdate = uint128(block.timestamp);` to **before** the external `borrowRate()` call (checks-effects-interactions), or cache and validate the returned rate:
```solidity
uint256 borrowRate = IIrm(marketParams.irm).borrowRate(marketParams, market[id]);
require(borrowRate <= MAX_BORROW_RATE, "rate too high"); // e.g., 1000% APR cap
```
  3. Consider a `ReentrancyGuard` on `_accrueInterest`-bearing external functions.

### [H-03] Callback Reentrancy Window in `supply` / `repay` / `liquidate` Before Token Transfer

- **Severity**: High
- **Vulnerability Type**: Reentrancy (state-before-transfer ordering)
- **Impact**: In `supply`, `repay`, and `liquidate`, the protocol updates all internal accounting and emits events **before** invoking the user callback and **before** pulling tokens via `safeTransferFrom`. A malicious callback can reenter Morpho and observe/act on state where the protocol *believes* it has already received assets it has not yet received. Concrete consequences:
  - **`supply`**: `totalSupplyAssets` and `supplyShares` are credited before `safeTransferFrom` completes. During `onMorphoSupply`, an attacker can `withdraw` using the not-yet-funded shares (if other liquidity exists), or `borrow` against phantom supply, or reenter `supply` to compound share credits. If the final `transferFrom` then fails, the whole tx reverts — but if the attacker arranges for the transfer to succeed *after* extracting value elsewhere in the same tx (e.g., via a flash loan covering the transfer), the inflated state persists.
  - **`liquidate`**: Collateral is transferred to the liquidator **before** the loan-token repayment is pulled. During `onMorphoLiquidate`, the liquidator already holds `seizedAssets` while `repaidAssets` is still owed. Reentering `liquidate` on the same or another borrower, or `withdraw`ing, can double-spend the not-yet-repaid value if the final `transferFrom` is satisfied by funds obtained during the callback (flash loan) — the ordering itself is safe only if every path's transfer ultimately succeeds, but intermediate reentrant actions see inconsistent balances.
  - **`repay`**: `borrowShares` burned and `totalBorrowAssets` reduced before funds arrive; reentrant `borrow` sees reduced debt with no corresponding cash.
- **Root Cause & Code Location**: `src/Morpho.sol` — `supply()`, `repay()`, `liquidate()`:
```solidity
// supply():
position[id][onBehalf].supplyShares += shares;
market[id].totalSupplyShares += shares.toUint128();
market[id].totalSupplyAssets += assets.toUint128();
emit EventsLib.Supply(...);
if (data.length > 0) IMorphoSupplyCallback(msg.sender).onMorphoSupply(assets, data); // <-- reentry
IERC20(marketParams.loanToken).safeTransferFrom(msg.sender, address(this), assets); // <-- funds arrive last
```
- **Proof of Concept (Foundry / Forge)**:
```solidity
contract ReentrantSupplier is IMorphoSupplyCallback {
    IMorpho immutable morpho;
    MarketParams mp;
    bool entered;

    function attack() external {
        morpho.supply(mp, 100e18, 0, address(this), abi.encode(uint8(1)));
    }

    function onMorphoSupply(uint256 assets, bytes calldata) external {
        if (entered) return;
        entered = true;
        // State already credits us 100e18 of supply shares, but Morpho holds 0 of our tokens yet.
        // Reenter: withdraw against the phantom shares (drains other suppliers' liquidity),
        // or borrow against the not-yet-funded position.
        morpho.withdraw(mp, 100e18, 0, address(this), address(this));
        // Final supply transferFrom will pull 100e18 from us at the end — but we've already
        // extracted 100e18 of someone else's liquidity in the same transaction.
    }
}
```
- **Remediation**: Enforce checks-effects-interactions strictly — pull tokens **before** crediting state, or add a reentrancy guard:
```solidity
// Option A: transfer first, then update state
IERC20(marketParams.loanToken).safeTransferFrom(msg.sender, address(this), assets);
position[id][onBehalf].supplyShares += shares;
market[id].totalSupplyShares += shares.toUint128();
market[id].totalSupplyAssets += assets.toUint128();
if (data.length > 0) IMorphoSupplyCallback(msg.sender).onMorphoSupply(assets, data);

// Option B: add to Morpho.sol
import {ReentrancyGuardTransient} from "openzeppelin-contracts/..."; // or a bool lock
modifier nonReentrant() { _; }
// Apply to supply, repay, liquidate, withdraw, borrow, withdrawCollateral, flashLoan.
```
Note: Morpho's official design *documents* this ordering and relies on the fact that a failed final `transferFrom` reverts the entire transaction — but reentrant actions that succeed *within* the callback window and are funded by flash liquidity still violate the invariant. A `nonReentrant` guard is the robust fix.

## Medium Severity Findings

### [M-01] `flashLoan` Allows Unrestricted Reentrancy Into All Morpho Functions

- **Severity**: Medium
- **Vulnerability Type**: Reentrancy
- **Impact**: `flashLoan` transfers tokens out, invokes an arbitrary callback on `msg.sender`, then pulls repayment. During the callback, the attacker holds Morpho's entire token balance and may call back into `supply`, `withdraw`, `borrow`, `liquidate`, `accrueInterest`, etc. on any market using that token. Because `withdraw`/`borrow` check `totalBorrowAssets <= totalSupplyAssets` against *accounting* totals (not actual balances), and `flashLoan` does not decrement any accounting, the attacker can't directly drain via accounting desync — but combined with oracle interactions or callback-ordering issues (H-03), it expands the attack surface. It also lets an attacker temporarily remove liquidity to manipulate utilization-driven IRMs (e.g., `IrmMock`'s utilization-based rate) within a block.
- **Root Cause & Code Location**: `src/Morpho.sol` — `flashLoan()`:
```solidity
IERC20(token).safeTransfer(msg.sender, assets);
IMorphoFlashLoanCallback(msg.sender).onMorphoFlashLoan(assets, data); // arbitrary reentry
IERC20(token).safeTransferFrom(msg.sender, address(this), assets);
```
- **Proof of Concept (Foundry / Forge)**:
```solidity
contract FlashReenter is IMorphoFlashLoanCallback {
    Morpho immutable morpho;
    function onMorphoFlashLoan(uint256 assets, bytes calldata data) external {
        // Morpho's loan token balance is now ~0 for this market.
        // Reenter: call accrueInterest / liquidate / borrow while liquidity is drained.
        morpho.borrow(marketParams, 1, 0, address(this), address(this));
        // Or manipulate utilization seen by a stateful IRM before it is re-accrued.
    }
}
```
- **Remediation**: Add a `nonReentrant` guard to `flashLoan` **and** to all state-changing external functions (or at minimum, block `flashLoan` reentry into `flashLoan` and into functions whose invariants assume token balances):
```solidity
modifier nonReentrant() { require(!locked, "reentrant"); locked = true; _; locked = false; }
function flashLoan(...) external nonReentrant { ... }
```

### [M-02] `setFeeRecipient` to `address(0)` Permanently Burns Protocol Fees

- **Severity**: Medium
- **Vulnerability Type**: Access Control / Logic Error
- **Impact**: `setFeeRecipient` only checks `newFeeRecipient != feeRecipient`. Setting it to `address(0)` is allowed. In `_accrueInterest`, `position[id][feeRecipient].supplyShares += feeShares` mints fee shares to `address(0)`. Those shares are unrecoverable — `withdraw` requires `receiver != address(0)` and `onBehalf` authorization, so the fees are permanently locked, reducing protocol revenue to zero with no revert. This is an owner-triggered griefing/loss scenario.
- **Root Cause & Code Location**: `src/Morpho.sol` — `setFeeRecipient()`:
```solidity
function setFeeRecipient(address newFeeRecipient) external onlyOwner {
    require(newFeeRecipient != feeRecipient, ErrorsLib.ALREADY_SET);
    feeRecipient = newFeeRecipient; // address(0) allowed
    ...
}
```
- **Proof of Concept (Foundry / Forge)**:
```solidity
function test_FeeRecipientZeroBurnsFees() public {
    morpho.setFeeRecipient(address(0));
    // Advance time, accrue interest on a market with fee > 0.
    morpho.accrueInterest(marketParams);
    // feeShares minted to address(0) — permanently unwithdrawable.
    assertEq(morpho.position(id, address(0)).supplyShares > 0, true);
}
```
- **Remediation**:
```solidity
require(newFeeRecipient != address(0), ErrorsLib.ZERO_ADDRESS);
```

### [M-03] `setAuthorizationWithSig` — Signature Malleability / Missing `chainid` Binding Is Partially Mitigated, but `ecrecover` Accepts High-`s` Signatures

- **Severity**: Medium
- **Vulnerability Type**: Cryptographic / Logic Flaw
- **Impact**: `ecrecover` returns `address(0)` on failure but does **not** reject malleable signatures (s-value in upper range, `v ∉ {27,28}`). While the `nonce` increment prevents replay of the *same* signature, a malleable variant of a valid signature is a *different* `(r,s,v)` that recovers the *same* signatory — it would pass `authorization.authorizer == signatory` and consume a *different* nonce only if the nonce matches. Since the nonce is checked against `authorization.nonce` (embedded in the struct, not the signature's), a malleable duplicate would fail the nonce check after the first use. The residual risk is low but
