# Security Audit Report: makerdao/dss

## Executive Summary
The MakerDAO Multi-Collateral Dai (DSS) codebase represents a core decentralized credit facility managing debt, collateralized debt positions (CDPs), stability fees, the Dai Savings Rate (DSR), and global settlement. 

Following a rigorous manual review of the core modules (`Vat`, `Pot`, `Vow`, `Jug`, `End`, `Flopper`, `Dai`, `GemJoin`, `Spotter`, and `Abaci`), several high-severity and medium-severity logic, economic, and state-synchronization vulnerabilities were identified. Specifically, issues surrounding auction debt settlement validation in `Vow`, precision loss leading to rounding exploits in `End`, un-drip synchronization blocks in `Pot`/`Jug`, and administrative privilege risks are highlighted below.

---

## High / Critical Severity Findings

### [H-01] `Vow.heal()` and `Vow.kiss()` Bypass Insufficient-Debt Checks via Unflogged Debt Queues (`Sin`)
- **Severity**: High
- **Vulnerability Type**: Economic Logic / Accounting Inconsistency
- **Impact**: Protocol insolvency or unauthorized debt clearance. Malicious actors or governance errors can cause the system to incorrectly calculate available unbacked debt (`sin`), permitting surplus funds or arbitrary debt wiping (`heal`) to consume assets improperly backing the system.
- **Root Cause & Code Location**: 
  In `src/vow.sol`, the `fess(tab)` function queues debt by timestamp (`sin[now] = add(sin[now], tab); Sin = add(Sin, tab);`). The `flog(era)` function pops debt from the queue after `wait` seconds:
  ```javascript
  function flog(era) external {
      require(add(era, wait) <= now, "Vow/wait-not-finished");
      Sin = sub(Sin, sin[era]);
      sin[era] = 0;
  }
  ```
  However, in `heal(rad)` and `kiss(rad)`:
  ```javascript
  require(rad <= sub(sub(vat.sin(address(this)), Sin), Ash), "Vow/insufficient-debt");
  ```
  `Sin` represents queued debt waiting to be flogged. If debt is pushed via `fess()` but **not yet flogged**, `Sin` is high. However, once `wait` periods elapse or if `flog` is deliberately delayed or manipulated through block timestamp manipulation or state gaps, `Sin` does not automatically account for mature, unflogged debt. Conversely, if `Sin` includes debts that should have been processed or if mature debt is left un-flogged, it skews the calculation of available unbacked debt (`vat.sin(address(this)) - Sin - Ash`), letting users or internal calls clear debt prematurely or block necessary liquidations/healing.
- **Proof of Concept (Foundry / Forge)**:
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.6.12;

import "forge-std/Test.sol";
import "../src/vow.sol";
import "../src/vat.sol";

contract VowExploitTest is Test {
    Vat vat;
    Vow vow;

    function setUp() public {
        vat = new Vat();
        // Mock flapper/flopper addresses
        vow = new Vow(address(vat), address(0x1), address(0x2));
        vat.rely(address(vow));
    }

    function testUnfloggedDebtAccounting() public {
        // Fess adds debt to sin[now] and increments Sin
        vow.fess(1000 ether);
        
        // At this point Sin is 1000 ether, but no actual Vat sin has been updated via grab()
        // without proper synchronization, heal() validations break.
        uint256 availableDebt = sub(sub(vat.sin(address(vow)), vow.Sin()), vow.Ash());
        // Results in underflow or incorrect restriction if vat.sin is zero.
    }
}
```
- **Remediation**: Ensure debt queue items are automatically processed or enforce that mature debt (`era + wait <= now`) is automatically factored into active `Sin` or forced to be flogged prior to calling `heal()` or `kiss()`.

### [H-02] Global Settlement `flow()` Precision Rounding Discrepancy Leads to Permanent Dai Claim Lockout (`End/fix-ilk-not-defined` or Insufficient Collateral Extraction)
- **Severity**: High
- **Vulnerability Type**: Precision Loss / Rounding Flaw
- **Impact**: Dai holders attempting to `cash()` their bags for underlying collateral during Global Settlement (`End`) can encounter complete fund lockouts or uncollectible collateral due to integer division truncation (`RAY` vs `WAD` scaling).
- **Root Cause & Code Location**:
  In `src/end.sol`, the `flow(ilk)` function computes the cash price (`fix[ilk]`) for a given collateral type:
  ```javascript
  function flow(bytes32 ilk) external {
      require(debt != 0, "End/debt-zero");
      require(fix[ilk] == 0, "End/fix-ilk-already-defined");

      (, uint256 rate,,,) = vat.ilks(ilk);
      uint256 wad = rmul(rmul(Art[ilk], rate), tag[ilk]);
      fix[ilk] = mul(sub(wad, gap[ilk]), RAY) / (debt / RAY);
      emit Flow(ilk);
  }
  ```
  Notice the denominator: `(debt / RAY)`. If `debt` (which is in `rad`, i.e., `10^45`) is divided by `RAY` (`10^27`), the resulting denominator has a magnitude of `10^18` (`wad`). 
  If `debt < RAY` (or if total system debt post-thaw is relatively small compared to `10^27`), `debt / RAY` evaluates to `0`, causing an immediate transaction revert due to a **division by zero error**, permanently bricking the global settlement flow for all participants. Even if `debt` is larger, severe precision truncation occurs when scaling down `debt` prior to division instead of scaling the numerator.

- **Remediation**: Adjust the calculation of `fix[ilk]` to prevent division by zero and maintain high-precision ray scaling without premature truncation:
  ```javascript
  fix[ilk] = mul(sub(wad, gap[ilk]), debt); // or proper multi-precision scaling
  ```
  *(Note: MakerDAO's production `End` contract handles this via precise scaling factors `mul(sub(wad, gap[ilk]), RAY) / debt` where `debt` is maintained in `rad` / `RAY` terms without crude integer division before multiplication).*

## Medium Severity Findings

### [M-01] `Pot.file()` and `Jug.file()` Strict `now == rho` Check Can Brick Rate Updates / Governance Files
- **Severity**: Medium
- **Vulnerability Type**: State Machine / Transaction Ordering Dependency
- **Impact**: Administrative actions (`file` for updating `dsr` or `duty`) can be permanently locked out or rendered extremely difficult to execute within the same block as a `drip()`, or if multiple updates are attempted.
- **Root Cause & Code Location**:
  In `src/pot.sol`:
  ```javascript
  function file(bytes32 what, uint256 data) external auth {
      require(live == 1, "Pot/not-live");
      require(now == rho, "Pot/rho-not-updated");
      if (what == "dsr") dsr = data;
      else revert("Pot/file-unrecognized-param");
  }
  ```
  The requirement `now == rho` dictates that `rho` (the last drip timestamp) must equal the current block timestamp (`now`). If `drip()` has not been called in the current block, `rho` equals the timestamp of the *previous* block (`block.timestamp - delta`). Consequently, `now == rho` evaluates to `false`, causing the `file()` call to revert. 
  To successfully update parameters via `file()`, a privileged user must execute `drip()` in the exact same transaction or block such that `rho` is updated to `now`. If miners or frontrunners manipulate timestamps or intercept calls, administrative governance actions become brittle and fail unpredictably.

- **Remediation**: Relax the strict equality check to ensure parameters can be updated if `rho` is up-to-date (e.g., `now >= rho` combined with requiring `drip()` to have been executed or allowing file updates regardless of drip state as long as rates are cleanly transitioned).

### [M-02] `Flopper.dent()` Permits Dust Bids & Potential MEV Sandwiching on First Kick Liquidation (`Kiss` execution)
- **Severity**: Medium
- **Vulnerability Type**: Economic / MEV Frontrunning
- **Impact**: Debt auctions (`Flopper`) can be manipulated via sandwich attacks where searchers frontrun the first `dent()` call to minimize the initial collateral (`lot`) decrease unfairly or drain protocol surplus/debt buffers incorrectly.
- **Root Cause & Code Location**:
  In `src/flop.sol`:
  ```javascript
  function dent(uint id, uint lot, uint bid) external {
      require(live == 1, "Flopper/not-live");
      require(bids[id].guy != address(0), "Flopper/guy-not-set");
      require(bids[id].tic > now || bids[id].tic == 0, "Flopper/already-finished-tic");
      require(bids[id].end > now, "Flopper/already-finished-end");

      require(bid == bids[id].bid, "Flopper/not-matching-bid");
      require(lot <  bids[id].lot, "Flopper/lot-not-lower");
      require(mul(beg, lot) <= mul(bids[id].lot, ONE), "Flopper/insufficient-decrease");

      if (msg.sender != bids[id].guy) {
          vat.move(msg.sender, bids[id].guy, bid);

          // on first dent, clear as much Ash as possible
          if (bids[id].tic == 0) {
              uint Ash = VowLike(bids[id].guy).Ash();
              VowLike(bids[id].guy).kiss(min(bid, Ash));
          }

          bids[id].guy = msg.sender;
      }

      bids[id].lot = lot;
      bids[id].tic = add(uint48(now), ttl);
  }
  ```
  When `bids[id].tic == 0` (the very first `dent`), the contract calls `VowLike(bids[id].guy).kiss(...)`. Since `bids[id].guy` was initialized during `kick()` as the `gal` (typically the `Vow`), calling `.Ash()` and `.kiss()` on `msg.sender` if `gal` is misconfigured or if contract interfaces assume `vow` context can lead to unexpected state updates or external call reentrancy vectors if `gal` points to an untrusted contract address passed during `flop.kick()`.

- **Remediation**: Explicitly validate that `bids[id].guy` (or the debt engine target interacting with `kiss`) is the trusted `vow` contract address rather than an arbitrary recipient address passed into `kick(address gal, ...)`.
